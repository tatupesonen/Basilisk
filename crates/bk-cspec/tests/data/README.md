# Test data for `bk-cspec`

| File | What it is | Provenance |
|---|---|---|
| `cspec_oracle.txt.gz` | What Ghidra's compiled reader made of every language/compiler pair the reference build's `.ldefs` list (294 pairs, 107 `.cspec` files; two V850 pairs fail in Ghidra itself and are recorded as `PAIRERR`): spaces, the registers the file names, data-organisation alignment, every model with its lists, entries, rules, shared actions, effects, likely trash, internal storage and ranges, payloads, defaults; and for one pair per `.cspec` file: storage assignment of every signature of `../oracle/signatures.txt` under every non-alias model, trial classification of generated trial sets (inputs and outputs), the list queries over a grid around every entry, `checkJoin`/`checkSplit`, and `hasEffect` around every effect. Format at the top of `../oracle/cspec_oracle.cc`. Read by `../oracle_replay.rs`. | Generated by `../oracle/regen.sh` from Ghidra commit `42db038f3c` (reference build objects rebuilt with `-ffp-contract=off`, `scripts/build-reference.sh`), Apple clang 17.0.0, macOS AArch64 (Darwin arm64), 2026-11-14. The generator is compiled with `-std=c++11 -fno-access-control -fsigned-char -ffp-contract=off`. |

Host dependence: no value involves floating point, `long`, or an unordered
or pointer-keyed container; pairs are in `.ldefs` order, models in name
order, everything else in list order, and no record depends on the order
C++ evaluates arguments. One thing in Ghidra itself is library-dependent:
`std::sort` of a model's effect list leaves records with equal addresses in
an order chosen by the C++ library (libc++ here, libstdc++ on Linux); the
replay compares effect lists as Ghidra holds them and lists any such case.
Regenerating on x86-64 Linux should give the same table unless a model has
two effects at one address.
